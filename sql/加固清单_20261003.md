### 为什么 2 和 3 自动解决了

**第 2 项**：`withdraw_company_value` 这个函数在新版里已经停用了（调用会返回
「新版已取消提取公司价值」）。老板想从公司拿钱只能走「分红」，而分红是
**按持股比例分给全体股东**的，不再是他一个人独吞。原来那个「股东的钱进了市值、
老板立刻提走」的路径从根本上不存在了。

**第 3 项**：注册公司现在**必须自己出资**（最低 20000，从余额真扣），
初始资金池就是他出的钱。原来「白送 20000 市值」的口子没了。

**而且 AMM 模型本身还有个额外好处**：池子是封闭的，任何一笔钱从哪来、到哪去
都能在 `stock_trades` 表里对上。想造币必须在某个环节凭空加钱，比旧模型难得多。

## 二、还需要做的 5 项

### 🔴 1. 买卖没有频率限制

**现状**：`buy_stock` / `sell_stock` 里没有任何频率约束。同一账号可以在
1 秒内调一百次。

**AMM 下的实际风险有多大**：
```
比旧模型小很多 —— 因为每次买卖都要吃手续费(5%)和滑点。
高频买卖只会让自己亏钱，不产生套利空间。
```
**但仍然值得加**，理由有两个：
```
· 防脚本 —— 有人在写自动化脚本反复调用，会给数据库造成无谓压力
· 防未来 —— 万一以后加了别的机制（比如手续费折扣、返利），高频就可能变成套利
```

**加固方案**：
```sql
-- 在 _orig_buy_stock / _orig_sell_stock 开头加
-- 每账号每公司：10 秒内最多 1 次买 + 1 次卖
SELECT count(*) INTO v_recent
  FROM public.stock_trades
 WHERE user_id = p_user_id AND company_id = p_company_id
   AND side = 'buy' AND created_at > now() - interval '10 seconds';
IF v_recent > 0 THEN RETURN '操作太频繁，请稍后再试'; END IF;

-- 每账号每日上限
SELECT count(*) INTO v_today
  FROM public.stock_trades
 WHERE user_id = p_user_id AND side = 'buy'
   AND created_at::date = (now() AT TIME ZONE 'Asia/Shanghai')::date;
IF v_today > 200 THEN RETURN '今日买入次数已达上限'; END IF;
```
`stock_trades` 表在重构时已经建好了，直接查就行，不用新建表。

### 🟡 4. 转账可以无限额

**现状**：`transfer_nb` 能一次性把全部余额转给小号。

**风险**：转账本身不造钱，但它让套利更容易启动 —— 你描述的刷币流程里
「大号没钱了小号转点」就是靠这个。

**AMM 下风险也变小了**（因为套利空间没了），但还有两个场景：
```
· 洗号：把一个号的余额瞬间搬到另一个号，规避封号/限额
· 配合自动抄底：一个号专门囤钱，多个号自动买入同一家公司
```

**加固方案**：
```
· 单笔上限 + 每日累计上限
· 新账号（注册 7 天内）不能转账，或限额很低
· 同一 IP 的账号互相转账时记日志，超阈值告警
```

### 🟡 5. 银行贷款细则不明（**我最不放心的一项**）

**现状**：`bank_loan` / `bank_credit_loan` 都直接给余额加钱，但我一直没看到
它们的线上定义，不知道额度上限和还款逻辑。

**这是唯一还没排查过的「直接加钱」入口。** 需要确认三件事：
```
① 有没有额度上限？上限跟什么挂钩（存款 / 等级 / 信用分）？
② 不还会怎样？有没有强制扣款或惩罚？
③ 能不能「贷出来 → 转给小号 → 大号不管了」这样赖账？
```

**如果这三个环节有空的，贷款就是【第二个造币口】** —— 而且比股票那个更直接。

**看定义**：
```sql
SELECT p.proname AS 函数名, pg_get_functiondef(p.oid) AS 定义
  FROM pg_proc p JOIN pg_namespace n ON n.oid = p.pronamespace
 WHERE n.nspname = 'public'
   AND p.proname IN ('bank_loan','bank_credit_loan','bank_repay','bank_repay_credit')
 ORDER BY p.proname;
```

### 🟢 6. 缺「全站货币总量」看门狗

**现状**：没有任何地方统计全站 NB币总量。

**为什么重要**：上次刷到 **90 亿亿**才被发现，就是因为没人盯着总量。
如果有个每天记录的数字，第一天就能看出异常。

**加固方案**：
```sql
-- 每天采样时顺手记一笔
INSERT INTO public.market_meta (key, value)
VALUES ('total_nb_' || to_char(now() AT TIME ZONE 'Asia/Shanghai','YYYY-MM-DD'),
        (SELECT sum(nb_balance)::text FROM public.profiles))
ON CONFLICT (key) DO UPDATE SET value = EXCLUDED.value;

-- 然后随时可以看趋势
SELECT key, value::numeric FROM public.market_meta
 WHERE key LIKE 'total_nb_%' ORDER BY key DESC LIMIT 30;
```
正常情况这个数字应该【基本持平】（只有签到、红包发放会让它缓慢增长）。
如果某天突然翻倍，就是有漏洞。

**可以顺手加个自动告警**：跟昨天比增长超过 10% 就写一条通知给管理员。

### 🟢 7. 缺「单账号余额异常」告警

**加固方案**：
```sql
-- 余额超过 1 亿就记一条给管理员
CREATE OR REPLACE FUNCTION public._balance_watchdog()
RETURNS void LANGUAGE plpgsql SECURITY DEFINER SET search_path TO 'public'
AS $$
DECLARE
    v_cap CONSTANT bigint := 100000000;    -- 1 亿
    r RECORD;
BEGIN
    FOR r IN SELECT id, username, nb_balance FROM public.profiles
              WHERE nb_balance > v_cap LOOP
        -- 每天最多提醒一次，避免刷屏
        IF NOT EXISTS (
            SELECT 1 FROM public.notifications
             WHERE user_id = r.id AND type = 'balance_alert'
               AND created_at > now() - interval '20 hours'
        ) THEN
            INSERT INTO public.notifications (user_id, type, title, content)
            VALUES (r.id, 'balance_alert', '余额异常提醒',
                    format('你的余额已达 %s NB币，请确认来源是否正常。', r.nb_balance));
        END IF;
    END LOOP;
END $$;
```
挂到 `market_tick_loop` 里顺手调一次就行（它每分钟跑）。

**正常玩不可能到 1 亿** —— 余额榜第 10 名才 1582 万。

## 三、AMM 重构后新增的观察项

这几条不是漏洞，但值得看一眼：

### A. 池子小于 30 万的公司永远不交税
```
公司税的门槛是 pool_cash >= 300000
注册公司最低出资 20000 → 池子 20000
如果没人买，它永远在 30 万以下 → 永远不交税
```
**影响**：可以无限注册「僵尸公司」占着名字。
**要不要管**：看你。真在意的话加个「注册满 N 天没交易就自动清算」。

### B. 反复注册 / 清清算不造币，但会刷屏
```
注册出 20000 → 拿 20000 张 → 立刻清算
池子 20000 按持股比例分 → 他持有 100% 的股东份额 → 拿回 20000
净变化：0（不造币，设计正确）
```
**但会在 `stock_trades` 里留下两条记录**。如果有人循环刷，日志会很脏。
**要不要管**：加个「清算后 N 天内不能重新注册」就够了。

### C. 大额买入的滑点告警是前端做的，后端没拦
```
前端：滑点 > 5% 标红提醒（只是提醒，不阻止）
后端：没有任何滑点保护
```
**要不要管**：可以在后端加个可选参数「最大可接受滑点」，
超过就拒绝。但 AMM 的滑点本来就是正常现象，强制拦可能引起困惑。
**建议不加**，靠前端提示就够了。
